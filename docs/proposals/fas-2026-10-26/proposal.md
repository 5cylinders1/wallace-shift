# Reusable publishing tools

## A Photo video and data components

I propose four reusable components within FAS.org's existing WordPress theme: an image carousel, an image grid, a video embed, and a featured data visualization. Each will use the site's existing typography, spacing, and visual conventions. I will review the theme and current editor first, then choose a custom block or template approach that fits how FAS already publishes.

The components will expose the fields staff need, such as images, captions, alternative text, headings, source links, and embed URLs. Layout choices will be limited enough to keep pages consistent while allowing staff to reuse the components in different contexts. Carousels will have keyboard controls and will not advance automatically by default.

The data component will support a responsive embed from FAS's existing Datawrapper or Tableau workflow, with space for a title, source, and accessible text or table alternative. Creating new datasets, custom chart engines, and recreating existing charts are outside this base item.

**Acceptance:** A FAS editor can add, edit, reorder, and remove each component on supported FAS.org pages and posts without editing code. We will demonstrate the components with FAS content at desktop and mobile widths and provide written instructions for each.

## B Social content on key page types

I recommend staff-selected posts from FAS's Instagram, LinkedIn, and X accounts, using supported embeds where available. Staff will select or replace a post through WordPress fields. This is a documented manual publishing process, submitted for FAS approval, rather than a subscription to an automated social feed.

One reusable social-content module will be available on the homepage, staff and fellow biography templates, and publication templates. A shared default can display FAS content across those templates; editors can choose different posts where needed. This avoids maintaining a separate account connection for every staff member or fellow.

Embeds will load only when needed. Each platform will have a readable fallback with an approved image or text excerpt and a source link if embedding is unavailable or fails the agreed accessibility or performance checks. The final presentation and staff workflow will be approved during planning.

**Acceptance:** Content from all three named platforms appears on the agreed page types, and a FAS editor can change it using the documented workflow. The base price assumes no new paid social-feed service or API subscription. Automated feeds, individual staff-account feeds, and bulk population of historical pages are not included.

# Program pages and site improvements

## C Program template and Future of Science pilot

I propose a program section within the existing FAS.org WordPress installation. A reusable landing-page layout and supporting page layout will give programs a consistent introduction, selected publications, media, contact information, and local navigation. Staff will be able to create another program section from the same layouts using written instructions.

The pilot includes one Future of Science landing page and up to four supporting pages populated with final copy and assets supplied by FAS. It includes two consolidated design review rounds before the layouts are approved. New components from item A can be used within the program pages.

The base fee also includes links in one shared navigation or header location on each of heatagenda.us, cri.fas.org, and essentialdata.us, connecting to FAS.org and the agreed program destination. These changes depend on access to each site's source and deployment process. Existing application behavior will be preserved.

**Acceptance:** The Future of Science section is live, its program navigation works, and a FAS editor can create and publish a second sample program section on staging. The three existing sister sites have the approved navigation links.

**Requested scope change:** This approach provides reusable program sections on FAS.org. It does not provision independent sites, domains, or WordPress installations. FAS must approve this interpretation of the microsite requirement. The existing sister sites will not receive the new WordPress blocks or social-content modules under the base fee.

## D Everyday site administration

On FAS.org, I will make footer links editable through WordPress, including social platforms and other external destinations. I will provide a WordPress-managed redirect workflow using an existing suitable tool or a supported free alternative, and display assigned publication tags through the publication template.

**Acceptance:** An authorized FAS editor can change a footer link, create and test a redirect, and see assigned tags on a publication without a code change. Documentation will cover permissions and the checks staff should make before publishing these changes.

## Boundaries of the base fee

FAS.org receives items A–D. The three named sister sites receive the navigation changes described above and discovery review. Their redesign, migration, application changes, or new CMS capabilities are excluded. Legacy sites, including nuke.fas.org and sgp.fas.org, are excluded.

Existing content remains in place. The fee includes pilot content entry and representative test examples, not an archive migration, a full content rewrite, bulk tagging, or accessibility remediation of historical pages and documents. # Testing and handoff

## Review the work in its publishing context

Testing will use examples from the pages staff actually manage: a publication, a biography, a standard page, and the Future of Science pilot. During discovery I will confirm the active templates, plugin dependencies, user roles, and release process with FAS and Gravitate. I will keep a record of the changes so another developer can understand and maintain them.

New templates and components will meet **WCAG 2.1 AA**. Checks will cover keyboard navigation, focus visibility, heading structure, labels, contrast, alternative text, zoom, and screen-reader behavior where relevant. Automated checks will supplement manual testing. FAS will supply accurate alternative text, captions, transcripts, and data summaries for its content; I will provide the fields and explain how to use them.

Third-party embeds will be reviewed as part of the complete component. Where a provider's output prevents an accessible presentation, we will use the approved accessible alternative. An inaccessible embed will not be treated as a completed deliverable merely because it loads.

## Browser and performance checks

I will test the new work in current Chrome, Safari, Firefox, and Edge, including responsive layouts and representative mobile use. Navigation, media, footer editing, redirects, and publication tags will be checked before release.

Before development, FAS and I will agree on representative pages, devices, network conditions, and repeatable page-load measurements. The acceptance target is no measurable deterioration from that baseline under equivalent test conditions. We will review repeated measurements to distinguish regressions from ordinary variation. Media sizing, deferred embeds, and restrained scripts will be part of implementation, not a separate optimization project.

Every release will be demonstrated on staging and require FAS approval. Before deployment I will confirm the hosting provider's backup and restore process and keep a rollback path for the changes being released. A short production check will follow each deployment.

## Staff handoff and warranty

Handoff includes source code and change history, access and configuration notes, instructions for every new component, the program-page setup guide, and a list of any third-party dependencies. Credentials will be transferred securely to FAS-controlled accounts.

One live remote training session of up to 90 minutes is included, with a recording if FAS permits. Staff will practice publishing a component, updating social content, creating a program section, and using the new administrative tools.

Defects in delivered work will be corrected at no charge for **60 days after final acceptance**, which will follow final launch. This warranty is not limited by an hourly allowance and does not require purchase of maintenance. New features and changes to the approved requirements will be estimated separately.
